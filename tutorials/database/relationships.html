Database: Relationships

Why PROTECT, CASCADE, and SET_NULL are each used where they are.

Every foreign key's on_delete is a deliberate choice, not the Django default left in place.

PROTECT — single-owner relationships

  • Organization.owner — an organization can't silently lose its owner.
  • Project.owner — same reasoning at the project level.
  • Project.workflow, Task.workflow_state — deleting a workflow/state a project or task actually depends on would silently corrupt that project/task's state; Django blocks the delete instead.

CASCADE — dependent rows that have no meaning without their parent

  • Membership rows (Membership, TeamMembership, ProjectMembership, TaskAssignment) — a membership without its organization/team/project/task is meaningless, so it's deleted along with its parent.
  • Team, Workflow, Project, Task, Label, Comment, WorkflowState, WorkflowTransition, ProjectExport — all CASCADE from their owning organization/project/task/workflow.

SET_NULL — high-cardinality attribution fields

  • Task.created_by, Comment.author, ActivityLog.actor, ProjectExport.requested_by — blocking every user deletion because they once created a task or left a comment would make account deletion impractical. The record is worth keeping even if authorship is lost.

GenericForeignKey — polymorphic targets

ActivityLog.target and Notification.target both use content_type + object_id to point at any model, not one fixed type — the same audit-log/notification row shape works whether the underlying event was a task, a comment, or a workflow change. See OOP → Polymorphism.
