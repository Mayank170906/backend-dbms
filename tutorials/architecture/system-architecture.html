System Architecture

Deployment topology and the multi-tenancy model that shapes everything else.

Deployment Topology

Every box is one compose service (dev: docker-compose.yml; prod: docker-compose.prod.yml). web/worker/beat share the same built image and source tree, differing only in their command.

In production, web runs on Render as the one deployed container; db is Supabase-hosted Postgres reached via DATABASE_URL rather than the compose db service. See Deployment Architecture for that variant.

Multi-Tenancy Model

"Tenant" in this system is the Organization. Everything else — teams, workflows, projects, tasks, comments, activity — hangs off an organization, directly or through a project. There is no shared/global data a tenant can accidentally see: every list endpoint's queryset is filtered by the caller's actual Membership/ProjectMembership rows, not by a permission check applied after fetching. A non-member requesting an object that exists but isn't theirs gets 404, not 403 — the object genuinely isn't in their queryset, so a 403 (which would confirm the object's existence) is never an option. See Permissions and API → Error Handling.

Every access-control check ultimately walks this chain back to a membership row for the requesting user.
