Low-Level Design

The ownership chain and app-by-app layout, one level below HLD.

This is the map that ties the abstract HLD boxes to actual Django apps. See Codebase → Applications for a one-paragraph purpose per app, and Models/ Services for full field/method detail — this page focuses on how the 9 apps relate to each other, not on repeating their internals.

App layout

apps/
├── accounts/       custom User model, JWT auth endpoints
├── organizations/  Organization, Membership, Team, TeamMembership
├── workflows/      Workflow, WorkflowState, WorkflowTransition
├── projects/       Project, ProjectMembership, ProjectExport
├── tasks/          Task, Label, TaskAssignment
├── comments/       Comment (+ @mention notifications)
├── activity/       ActivityLog (immutable audit trail)
├── notifications/  Notification (+ WebSocket broadcast)
└── analytics/      cross-model full-text search (no models of its own)

Dependency direction

Dependencies flow one way, matching the ownership chain from System Architecture: accounts is depended on by everything (the user FK); organizations is depended on by workflows and projects; projects is depended on by tasks; tasks is depended on by comments. activity and notifications are depended on by every other app's service layer (they're called, they don't call back), and analytics only reads from the other apps' models — nothing depends on it.

Cross-cutting: caching

apps/projects/statistics.py computes project statistics (completion rate, per-day histogram, overdue count, workload by member) from real aggregate queries, then apps/projects/caching.py caches the result in Redis for 300 seconds (PROJECT_STATISTICS_CACHE_TTL). apps/tasks/signals.py invalidates that cache on every Task/TaskAssignment save or delete — a classic cache-aside pattern, not a scheduled refresh.
