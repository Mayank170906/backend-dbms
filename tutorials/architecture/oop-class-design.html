OOP / Class Design

Every classic OOP idea, shown with the actual class from this project that demonstrates it — not a textbook example.

Inheritance

The custom User model inherits from Django's AbstractUser, gaining username/password/permission handling for free while adding only what's actually new:

class User(AbstractUser):
    email = models.EmailField("email address", unique=True)
    avatar = models.ImageField(upload_to="avatars/", blank=True, null=True)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

Every model in the system inherits from django.db.models.Model the same way — inheriting field descriptors, the query manager, save()/delete(), and migration machinery, then overriding only what needs to differ (see Polymorphism below for an example that overrides save()/delete() entirely).

Encapsulation

The service layer is encapsulation applied at the architecture level: a caller (a view, a management command, a test) never manipulates a task's assignment rows directly — it calls TaskService.assign(), which hides how that's validated and persisted:

class TaskService:
    @classmethod
    @transaction.atomic
    def assign(cls, *, task: Task, user, actor) -> TaskAssignment:
        cls._ensure_project_member(project=task.project, user=user)
        assignment, created = TaskAssignment.objects.get_or_create(task=task, user=user)
        if created:
            ActivityService.log(...)
            NotificationService.notify(...)
        return assignment

The _ensure_project_member check is a private implementation detail (the leading underscore is Python's convention for "internal") — callers depend on the public interface (assign(task=, user=, actor=)), not on how membership happens to be verified today.

Polymorphism

Django's GenericForeignKey is polymorphism at the data layer: an ActivityLog row's target can point at a Task, a Comment, a Workflow, or anything else — the same field, the same serializer code, resolving to a different concrete type per row:

class ActivityLog(models.Model):
    content_type = models.ForeignKey(ContentType, on_delete=models.CASCADE)
    object_id = models.PositiveBigIntegerField()
    target = GenericForeignKey("content_type", "object_id")

Method overriding is the more classic form of polymorphism, and ActivityLog demonstrates that too — it overrides save() and delete() from the base Model class to change their behavior entirely (raising instead of writing), while every other model relies on the inherited default:

def save(self, *args, **kwargs):
    if self.pk is not None:
        raise ValueError("ActivityLog entries are immutable and cannot be updated.")
    super().save(*args, **kwargs)

def delete(self, *args, **kwargs):
    raise ValueError("ActivityLog entries cannot be deleted; they are a permanent audit trail.")

Django REST Framework's ModelViewSet is the same idea one layer up: every viewset in this project (TaskViewSet, ProjectViewSet, …) inherits the same list()/ create()/retrieve()/update()/ destroy() methods, and each overrides only get_queryset() and perform_create() to supply its own scoping and validation — the HTTP dispatch logic itself is never rewritten.

Abstraction

A view never knows how a workflow transition is validated — only that calling WorkflowService.transition_task() either succeeds or raises a specific, meaningful exception:

try:
    WorkflowService.transition_task(task=task, to_state=to_state, user=request.user)
except ValueError as exc:
    raise ValidationError(str(exc))
except PermissionError as exc:
    raise PermissionDenied(str(exc))

Everything about sequential-state checking, role-list lookups, and audit logging is abstracted behind that one call — the API view's job is only to translate the two exception types into the right HTTP status codes.

Composition Over Inheritance

Rather than a deep inheritance hierarchy of viewsets, this project composes behavior via DRF's mixins and pluggable backends — filter_backends, permission_classes, and DRF's own mixin classes are all assembled onto a viewset rather than inherited from a specific parent:

class TaskViewSet(viewsets.ModelViewSet):
    permission_classes = [permissions.IsAuthenticated]
    filter_backends = [DjangoFilterBackend, SearchFilter, OrderingFilter]
    filterset_class = TaskFilter

NotificationViewSet composes even more explicitly, picking only the two mixins it needs (list + retrieve) instead of the full ModelViewSet, since notifications are never created or deleted through the API directly:

class NotificationViewSet(mixins.ListModelMixin, mixins.RetrieveModelMixin, viewsets.GenericViewSet):
    ...

Class Methods vs. Static Methods vs. Instance Methods

The service classes in this project are never instantiated — every method is a @staticmethod or @classmethod, because a service has no per-instance state to hold (unlike a model instance, which is a row of data). A @classmethod is used specifically when a method needs to call another method on the same class (like create_organization calling cls._unique_slug(...)):

class ProjectService:
    @staticmethod
    def _unique_slug(*, organization, name: str) -> str: ...

    @classmethod
    @transaction.atomic
    def create_project(cls, *, organization, owner, name, description="") -> Project:
        cls._ensure_organization_member(organization=organization, user=owner)
        project = Project.objects.create(..., slug=cls._unique_slug(organization=organization, name=name))
        ...
