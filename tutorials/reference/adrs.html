Architecture Decision Records

Meaningful architectural decisions, each with context, reasoning, alternatives, and current status.

ADR-001 — Django + Django REST Framework

Context: need a batteries-included framework with a mature ORM, admin, and auth for a project management platform.

Decision: Django + DRF for the entire backend.

Reason: ORM + migrations + admin out of the box; DRF adds serializers/viewsets/permissions/pagination without reinventing them.

Alternatives considered: Flask/FastAPI + a separate ORM — more assembly required for equivalent features.

Consequences: tied to Django's request/response and ORM conventions throughout. Status: Accepted, implemented.

ADR-002 — PostgreSQL over MySQL/SQLite

Context: need full-text search and a small unordered set field without extra join tables.

Decision: PostgreSQL as the only supported database.

Reason: SearchVectorField/GinIndex and ArrayField are used directly by real models.

Alternatives considered: MySQL (no native full-text-search-as-good, no ArrayField), SQLite (concurrency limits under multi-process writes).

Consequences: not database-agnostic by design. Status: Accepted, implemented.

ADR-003 — JWT over session-based authentication

Context: a JSON API consumed by a JS frontend and, potentially, external clients.

Decision: djangorestframework-simplejwt with access+refresh tokens, no server-side session store for the API.

Reason: statelessness across the web/worker processes, no CSRF dance for non-form requests.

Alternatives considered: Django session auth — would need shared session storage and CSRF handling for a pure-JSON API.

Consequences: WebSocket auth needs a separate token-in-query-string path. Status: Accepted, implemented.

ADR-004 — A per-app service layer

Context: business rules (membership checks, transaction boundaries, audit logging) must hold no matter which code path triggers them (API, management command, future task).

Decision: every app's write logic lives in a services.py, never directly in a view/serializer.

Reason: a rule in a view only fires for that exact endpoint; a rule in a service fires for every caller.

Alternatives considered: "fat models" (business logic as model methods) — harder to compose transactions spanning multiple models.

Consequences: more indirection for simple CRUD, real payoff for anything with side effects. Status: Accepted, implemented consistently.

ADR-005 — Docker + uv for dependency management

Context: need reproducible builds and a single deployable artifact.

Decision: uv + pyproject.toml/uv.lock, packaged into one Docker image used for web/worker/beat.

Reason: exact pinned dependency resolution; one image, three roles, differing only by container command.

Alternatives considered: plain pip + requirements.txt — weaker lock-file guarantees.

Consequences: adds a build-time-only dependency-install layer distinct from the runtime image. Status: Accepted, implemented.

ADR-006 — Render + Supabase for hosting

Context: need a hosted, low-maintenance production target.

Decision: Render runs the Docker image; Supabase hosts PostgreSQL, connected via DATABASE_URL.

Reason: avoids self-managing a database server; Render's Docker-native deploy matches the project's existing containerization.

Alternatives considered: self-hosted Postgres on the same host as the app — couples app and database lifecycle unnecessarily.

Consequences: Redis/Celery/Channels need separate provisioning if used in this environment — see Current Status. Status: Accepted, implemented (web service only).

ADR-007 — One Redis instance, four logical databases

Context: cache, Celery broker, Celery result backend, and the Channels layer each need a Redis-backed store.

Decision: one Redis server, four separate numbered DB indexes (0/1/2/3).

Reason: a development-time FLUSHDB on one logical store can't wipe the others; avoids running four separate Redis processes.

Alternatives considered: a dedicated Redis instance per concern — more operational overhead for a project this size.

Consequences: all four still share one physical instance's memory/availability. Status: Accepted, implemented.

ADR-008 — ASGI/Daphne to serve both HTTP and WebSocket

Context: the app needs both a JSON REST API and real-time WebSocket feeds.

Decision: one ASGI application (config/asgi.py), served by Daphne, routes both protocols.

Reason: Django Channels requires ASGI; running one process for both protocols is simpler to deploy than a separate WebSocket server.

Alternatives considered: WSGI + a separate WebSocket service — two deployable units instead of one.

Consequences: the whole app is ASGI-based even where a request is plain synchronous HTTP. Status: Accepted, implemented.
