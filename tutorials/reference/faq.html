Frequently Asked Questions

Why this choice and not the obvious alternative — the tradeoffs behind the code.

Database & Data Modeling

Why PostgreSQL and not MySQL or SQLite?

Two features this project actually uses, not just "Postgres is popular": a stored, GIN-indexed SearchVectorField for real full-text search, and ArrayField for WorkflowTransition.allowed_roles. Both would need either a separate search service or an extra join table on MySQL/SQLite. SQLite specifically also can't hold up under concurrent writes the way this system needs once Celery workers and the web process are writing at the same time.

Why is Task.workflow_state a foreign key instead of a status string with choices?

Because the spec (and any real project management tool) needs administrator-defined workflows — different teams genuinely run different pipelines. A hardcoded choices=[...] field can't do that without a code change and migration every time someone wants a new state. Modeling Workflow/WorkflowState/WorkflowTransition as real tables makes the pipeline itself configurable data.

Why do some foreign keys use PROTECT and others SET_NULL?

PROTECT is for genuine single-owner relationships — an Organization or Project needs exactly one accountable owner, and losing that silently is a bug, not a feature. SET_NULL is for high-cardinality attribution fields like Task.created_by — blocking every user deletion because they once filed a task would make account deletion impractical in real use. The task is worth keeping even if authorship is lost.

Why is Project.slug unique per-organization instead of globally?

Two unrelated tenants both naming a project "backend" is normal and shouldn't collide. Project URLs are scoped under their organization anyway, so global uniqueness would be an artificial constraint serving a URL scheme this app doesn't even use.

API & Security

Why does a non-member get 404 instead of 403?

A 403 confirms the resource exists — that's an information leak in a multi-tenant system, since it tells an attacker "this id is a real project, you just can't see it." Scoping the queryset itself (rather than fetching-then-checking-permission) means the resource genuinely isn't there for a non-member, so a 404 is both simpler and more honest.

Why JWT instead of session-based authentication?

Statelessness: no server-side session store to scale or share across the web/worker processes, and no CSRF token dance for a JSON API that isn't submitted from an HTML form. The tradeoff is that a WebSocket handshake can't carry a custom Authorization header, so the token travels as a query parameter for that one case instead — the standard workaround for JWT-over-WebSocket.

Why does the password-reset endpoint always return 200?

If it returned 404 for an unregistered email, an attacker could enumerate every real account one guess at a time. An identical response either way costs a legitimate user nothing and closes that leak.

Why is there both a queryset filter AND a permission class checking membership?

They answer different questions. The queryset answers "does this resource exist for this caller at all" (IDOR protection — a non-member never even reaches the object). The permission class answers "given that they can see it, are they allowed to do this specific write" (e.g. only a Manager can update an organization's settings, even though any member can view them).

Caching, Async & Real-Time

Why cache-aside instead of updating the cache on every write?

Write-through would mean recomputing the (fairly expensive) statistics aggregate on every task edit, whether or not anyone is currently looking at that project's dashboard. Cache-aside only pays that cost when a read actually happens after something changed — which matches real usage, since dashboards are viewed far less often than tasks are edited.

Why invalidate the cache with a signal instead of calling invalidate() in each service?

A signal attaches the correctness property ("the cache reflects the database") to the model, not to a list of call sites. An explicit call in TaskService.create_task would work today but silently stop working the moment someone edits a task through the Django admin, a script, or a future code path nobody remembered to update.

Why Celery instead of just running background work in a thread?

A thread dies with the request process — if the server restarts mid-export, the work is gone with no record it ever ran. Celery gives a durable queue (Redis), a separate worker process that can scale independently of the web process, retries, and — critically for this project — a trackable ProjectExport row the API can hand back immediately while the real work happens elsewhere.

Why is broadcasting deferred with transaction.on_commit() instead of happening immediately?

Every caller of ActivityService.log()/NotificationService.notify() already runs inside transaction.atomic(). Broadcasting synchronously at the point of .create() would mean a live WebSocket event fires for a database row that might not exist a moment later, if something else in the same transaction fails and rolls it back. on_commit() guarantees a client only ever sees an event for a change that's actually, durably true.

Architecture & Process

Why a service layer instead of putting logic in views/serializers?

A rule that lives only inside a DRF view only fires when that exact HTTP endpoint is hit. The seed-data management command, a future Celery task, and the Django admin all need "assigning a task validates project membership" to hold too — putting it in TaskService means every one of those call sites gets it automatically, for free, forever.

Why does the frontend use plain HTML/CSS/JS instead of React or a framework?

The project's stated focus is backend/database engineering — the frontend exists to prove the API is actually usable end to end, not to showcase frontend framework skills. A build-free vanilla JS frontend also makes a point about the API's own quality: every page is just fetch() calls against the same /api/v1/ surface any external client would use — no special access, no shortcuts through the ORM.

Why did testing catch bugs in already-shipped code?

Two real examples the README documents: TaskService's cross-project label validation only ran on the create path — ModelViewSet's default update() calls serializer.save() directly and never touches the service layer, so a plain PATCH could bypass it entirely, until TaskSerializer.validate_labels was added to close that gap. The lesson generalizes: a rule enforced in only one of several possible entry points isn't really enforced; it's enforced by circumstance.
