Developer Notes: Deployment Notes

Container networking, build-time vs. run-time env vars, and one ASGI app for both protocols.

Why 127.0.0.1 fails inside a container

Inside a container, 127.0.0.1 means the container itself — not the host machine, and definitely not a separately-hosted database like Supabase. This is the single most common deployment mistake this project's docs call out; see Deployment → Troubleshooting.

Build-time vs. run-time environment

A Docker image is built once and run many times (or on a different host entirely, as with Render building then running the same image). Anything a build step needs — like collectstatic needing some value for settings that validate their presence — has to be satisfiable without the real runtime secrets, which is why the Dockerfile uses throwaway placeholders for that one RUN step.

One ASGI app serves both HTTP and WebSocket

config/asgi.py's ProtocolTypeRouter is why a single Daphne process (and a single Render service) can serve /api/v1/... and ws://.../ws/... at once — there's no separate WebSocket server or port to manage in production.
