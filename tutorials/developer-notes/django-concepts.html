Developer Notes: Django Concepts

Settings, apps, models, migrations, URLs — taught with this project's real code.

Settings as a package, not a file

Most tutorials show one settings.py. This project splits it into base.py/development.py/production.py specifically so "what's different between dev and prod" is a small, readable diff instead of scattered if DEBUG: branches. See Codebase → Configuration.

Apps are namespaced packages, not just directories

Every app here is registered as apps.<name> (e.g. AppConfig.name = "apps.tasks"), which is why INSTALLED_APPS lists "apps.tasks" rather than bare "tasks" — this avoids import-name collisions with any third-party package that happens to also be called tasks.

Custom user model, from day one

AUTH_USER_MODEL = "accounts.User" is set before the first migration ever runs. Swapping the user model after real data exists is notoriously painful in Django — this project sidesteps that by never using the default auth.User at all, even though User(AbstractUser) only adds a unique email and an avatar on top of it.

Migrations as a history, not a snapshot

Each app's migrations/ directory is an ordered log of schema changes. The three full-text-search migrations (see Database → Migrations) are a good example of a migration doing more than a field add — they also create GinIndexes, which Django expresses as their own migration operations.

URLs resolve top-down, then hand off

config/urls.py includes config/api_router.py at api/v1/; the router then does its own dispatch to the right viewset action. Two levels of URL resolution, not one flat list — see Codebase → URLs.
