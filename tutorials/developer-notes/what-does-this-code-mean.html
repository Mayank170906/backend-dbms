WorkflowService.transition_task

@classmethod
@transaction.atomic
def transition_task(cls, *, task, to_state, user):
    cls._ensure_project_member(project=task.project, user=user)
    transition = WorkflowTransition.objects.filter(
        workflow=task.workflow_state.workflow if task.workflow_state else to_state.workflow,
        from_state=task.workflow_state,
        to_state=to_state,
    ).first()
    if transition is None:
        raise ValueError("No such transition is defined for this workflow.")
    role = ProjectMembership.objects.get(project=task.project, user=user).role
    if transition.allowed_roles and role not in transition.allowed_roles:
        raise PermissionError("Your role cannot perform this transition.")
    task.workflow_state = to_state
    task.save(update_fields=["workflow_state"])
    ActivityService.log(...)
    NotificationService.notify(...)
    return task

@classmethod because it needs to call other classmethods on the same class; @transaction.atomic because a transition, its activity log entry, and its notification must all succeed or all roll back together. The membership check runs first — a non-member never even gets to the "is this transition valid" question. Looking up the WorkflowTransition by (workflow, from_state, to_state) is what makes "skip a state" or "enter at a non-initial state" fail: if no row matches that exact triple, there's no valid path, full stop.

TaskViewSet's custom actions

@action(detail=True, methods=["post"])
def assign(self, request, pk=None):
    task = self.get_object()
    serializer = TaskAssignSerializer(data=request.data)
    serializer.is_valid(raise_exception=True)
    user = User.objects.get(pk=serializer.validated_data["user_id"])
    TaskService.assign(task=task, user=user, actor=request.user)
    return Response(TaskSerializer(task).data)

@action(detail=True, ...) registers this at tasks/{pk}/assign/ rather than a top-level route — DRF's router wires that up automatically from the decorator, no manual URL entry needed. self.get_object() re-uses the same scoped queryset every other action on this viewset uses, so a non-member still gets 404 here too, not a special-cased check. The view's own job stops at "validate the input shape, then hand off" — TaskService.assign does the actual work.

ActivityLog's save()/delete() override

def save(self, *args, **kwargs):
    if self.pk is not None:
        raise ValueError("ActivityLog entries are immutable and cannot be updated.")
    super().save(*args, **kwargs)

def delete(self, *args, **kwargs):
    raise ValueError("ActivityLog entries cannot be deleted; they are a permanent audit trail.")

self.pk is not None is how Django's ORM distinguishes an update from an insert — a fresh instance has no primary key yet. Raising instead of updating turns "someone tried to edit an audit log entry" from a silent bug into an immediate, loud failure. delete() is simpler still: there is no legitimate reason to ever call it, so it always raises.

JWTAuthMiddleware (WebSocket auth)

class JWTAuthMiddleware(BaseMiddleware):
    async def __call__(self, scope, receive, send):
        query = parse_qs(scope["query_string"].decode())
        token = query.get("token", [None])[0]
        scope["user"] = await self._get_user(token)
        return await super().__call__(scope, receive, send)

This is Channels' ASGI middleware pattern, not Django's HTTP middleware — it wraps the connection scope once, at connect time, rather than running per-message. Parsing the token out of scope["query_string"] is the workaround for a browser's WebSocket API not supporting custom headers during the handshake. Setting scope["user"] is what lets ProjectConsumer/ NotificationConsumer later check self.scope["user"] exactly like a view checks request.user.
