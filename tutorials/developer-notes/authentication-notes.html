Developer Notes: Authentication Notes

Access vs. refresh tokens, rotation, and why WebSocket auth is a separate code path.

Access token vs. refresh token

The access token (30 minutes) is what's checked on every request; the refresh token (7 days) exists only to get a new access token without forcing a re-login. Never send the refresh token as a bearer credential on a normal API call — it's only ever posted to login/refresh/.

Why rotation + blacklist together

ROTATE_REFRESH_TOKENS means every refresh call issues a brand-new refresh token; BLACKLIST_AFTER_ROTATION means the old one is immediately invalidated. Together, a refresh token can only ever be used once — if an attacker and the real user both try to use the same (stolen) refresh token, whichever uses it second gets rejected outright, which is itself a signal something is wrong.

Why WebSocket auth is a different code path

DRF's JWTAuthentication only runs inside the HTTP request/response cycle. A WebSocket handshake is a plain HTTP upgrade request from a browser that can't attach a custom Authorization header — so config/channels_auth.py::JWTAuthMiddleware reads the token from ?token= instead and validates it with SimpleJWT's AccessToken class directly, setting scope["user"] for the consumer to use.
