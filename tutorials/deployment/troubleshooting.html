Deployment: Troubleshooting

Real problems, their cause, and the fix.

connection to server at "127.0.0.1", port 5432 failed: Connection refused

Django is trying to connect to Postgres on localhost instead of reading DATABASE_URL. Point DATABASE_URL at the real database (Supabase in production) and confirm the settings module actually parses it.

DATABASE_URL missing during Docker build

RuntimeError: DATABASE_URL environment variable must be set in production. — raised because the Docker build runs a Django management command before Render's runtime environment exists. Let build-time commands like collectstatic run against a placeholder DATABASE_URL (see the Dockerfile's RUN step) instead of hard-requiring it via os.environ[...].

Invalid HTTP_HOST header

The deployment's hostname is missing from ALLOWED_HOSTS, or was entered with an https:// prefix (Django rejects a scheme in this setting). Use the bare hostname.

Boot log shows "using settings 'config.settings.development'"

DJANGO_SETTINGS_MODULE isn't set to config.settings.production in the deployment's environment — check for a hardcoded default in manage.py/wsgi.py/asgi.py or the compose/Render command.

"You have N unapplied migration(s)"

Normal for a freshly provisioned database. Run python manage.py migrate against it — ideally as a release/pre-deploy step rather than manually after each deploy. See Database → Migrations.

Static files missing / unstyled admin

collectstatic didn't run, or STATIC_ROOT/WhiteNoise's STORAGES["staticfiles"] isn't configured. This project's Dockerfile always runs collectstatic at build time, so this usually means a customized image skipped that step.

Redis connection refused

Django/Celery/Channels is trying redis://localhost:6379 in an environment with no Redis service. Provision a real Redis instance and point REDIS_URL/CACHE_URL/CELERY_BROKER_URL/CHANNELS_REDIS_URL at it, or accept those features are unavailable in that deployment — see Current Status.

Container exits immediately / never becomes healthy

Check docker/entrypoint.sh's Postgres-readiness loop isn't stuck (30 retries, 1s apart) — usually means DATABASE_URL/POSTGRES_HOST points at a database that isn't actually reachable from the container's network.
