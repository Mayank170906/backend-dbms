Deployment: Supabase

PostgreSQL's role, the Session Pooler connection, and why the API keys aren't the database.

Supabase's only role in this project is hosting the PostgreSQL database — the app doesn't call the Supabase API for anything else.

Connection

In Supabase: Project → Connect gives the Postgres connection info. For a persistent backend like this one, the Session Pooler connection is the one to use — it works even when the deployment environment only has IPv4 connectivity. 

postgresql://postgres.xxxxx:YOUR_PASSWORD@aws-0-region.pooler.supabase.com:5432/postgres

If Supabase gives a placeholder like [YOUR-PASSWORD], replace it with the real password (brackets removed) and URL-encode any special characters. Use the string Supabase generates rather than hand-building one, and never commit it to GitHub.

Database credentials ≠ API keys

Supabase also issues API-level variables — SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY, SUPABASE_JWKS_URL. Those are unrelated to DATABASE_URL and this project's own JWT auth (API → Authentication) doesn't use them — don't substitute one for the other.
