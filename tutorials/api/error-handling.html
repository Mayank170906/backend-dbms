API: Error Handling

The custom error envelope and the 404-vs-403 IDOR-safe pattern.

config/exceptions.py::custom_exception_handler wraps every DRF error response in a consistent envelope: 

{
  "error": {
    "status_code": 400,
    "detail": "..."
  }
}

Standard status codes

CodeWhen
400Serializer validation failure, e.g. cross-project label on a task
401Missing/invalid/expired JWT
403Authenticated, a member of the resource's tenant, but the wrong role for the action (object-level permission failure)
404Object doesn't exist or the caller isn't a member of its organization/project — deliberately indistinguishable
429Throttle exceeded (user/anon/auth scopes)

Why 404, not 403, for non-members

A 403 confirms an object exists — in a multi-tenant system that's an information leak (it tells a caller "this ID is real, you just can't see it"). Every list/detail queryset is filtered by the caller's actual membership rather than fetched-then-permission-checked, so a non-member's object genuinely isn't in the queryset — a 404 is the honest answer, not a deliberately vague one. Verified directly by tests/test_security_idor.py.
