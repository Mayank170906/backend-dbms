1. Introduction

1.1 Purpose

This document specifies the functional and non-functional requirements for a multi-tenant workflow and project management platform. It exists to make the system's scope and behavior explicit and testable — every requirement maps to real code (see Traceability Matrix).

1.2 Scope

The system lets an organization manage projects, tasks, and configurable workflows, with role-based authorization, real-time updates, background processing, and full-text search. It is backend-first: a REST API is the source of truth, and a bundled server-rendered frontend consumes that same API rather than the database directly.

2. Overall Description

2.1 Product Perspective

A new, self-contained system — not an extension of an existing product. It intentionally mirrors the feature shape of Jira/Linear/Trello (projects, tasks, configurable workflows, activity feeds) while using its own data model and implementation throughout.

2.2 Product Functions

  • User registration, authentication (JWT), and password recovery
  • Organization creation and role-based membership management
  • Team management within an organization
  • Project creation, membership, and status tracking
  • Task creation, assignment, labeling, and commenting (with @mentions)
  • Administrator-defined workflows (states + role-gated transitions)
  • An immutable activity/audit log for every significant action
  • In-app notifications, delivered live over WebSocket
  • Cached, on-demand project statistics and analytics
  • PostgreSQL full-text search across tasks, projects, and comments
  • Asynchronous CSV export of a project's tasks
  • Periodic background jobs (due-date reminders, daily reports, token cleanup)

2.3 User Classes and Characteristics

See Actors for the full table.

2.4 Operating Environment

Server-side: Python 3.12, Django, PostgreSQL 16, Redis 7, run as Docker containers orchestrated by Docker Compose. Client-side: any modern browser (the bundled frontend uses vanilla JS, the Fetch API, and native WebSockets — no framework, no build step).

2.5 Design and Implementation Constraints

  • No paid third-party APIs or services may be required to run the system.
  • PostgreSQL is the only supported database backend (the system deliberately uses Postgres-specific features — full-text search, array fields — rather than staying database-agnostic).
  • All business rules must be enforced server-side; the frontend is never trusted as an authorization boundary.

2.6 Assumptions and Dependencies

Assumes a single PostgreSQL instance and a single Redis instance are reachable from every backend process. Assumes clients can maintain a persistent WebSocket connection for real-time features to be useful (the system remains fully functional over plain HTTP polling otherwise).

4. External Interface Requirements

4.1 API Interface

A versioned REST API under /api/v1/, documented via an OpenAPI schema at /api/schema/ and a browsable Swagger UI at /api/docs/. JSON request/response bodies throughout, JWT bearer-token authentication, consistent pagination and error response shapes.

4.2 WebSocket Interface

Two endpoints under /ws/ — a per-project activity feed and a per-user notification stream — authenticated via a JWT passed as a query parameter.

4.3 User Interface

A server-rendered set of HTML pages (dashboard, organization detail, project detail with a Kanban board, notifications, search) that consume the same REST/WebSocket API as any external client would.
