User Workflows

What a real user actually does, end to end — and what the system does in response at each step.

1. Onboarding

  1. User registers with username, email, password. Password is validated (length, similarity, common-password checks) and hashed before storage.
  2. User logs in and receives a JWT access token (30 min) and refresh token (7 days).
  3. The frontend stores both and attaches the access token as a Bearer header on every subsequent request.

2. Setting Up an Organization

  1. User creates an organization. They become its Owner automatically — this happens in one atomic transaction so the org can never exist without its owner's membership row.
  2. Owner invites teammates by username, choosing a role for each (Admin / Member / Viewer).
  3. Optionally, the owner creates Teams within the organization to group people.

3. Setting Up a Project

  1. Any organization member creates a project. The creator becomes its Manager.
  2. Manager adds project members from among the organization's members.
  3. Manager either creates a new Workflow for the project or attaches an existing one from the organization.

4. Configuring the Workflow

  1. Manager defines states — e.g. Backlog (initial) → Todo → In Progress → Code Review → Done (terminal).
  2. Manager defines which transitions are legal between which states, and which roles may perform each one.
  3. From this point on, the backend — not the frontend — is the sole authority on which moves are legal.

5. Working with Tasks

  1. A project member creates a task: title, description, priority, optional due date and estimated hours.
  2. The task starts with no workflow state (workflow_state = null) until someone moves it into the workflow's initial state.
  3. Members assign the task, attach labels, and comment (typing @username to mention and notify a teammate).
  4. A member moves the task through states one legal transition at a time — skipping a state, entering at a non-initial state, or using a role the transition doesn't permit is rejected with a clear error.

6. Staying Informed

  • Every significant action writes an immutable activity log entry, visible live over WebSocket to anyone with that project's Activity tab open.
  • The affected user gets an in-app notification for anything that concerns them directly — again live over WebSocket.
  • A daily background job notifies assignees of tasks due the next day, and sends project owners a daily summary.

7. Reviewing & Reporting

  • A project's Statistics tab shows task counts, breakdowns, workload per member, and completion time — computed from Postgres, cached in Redis, refreshed the moment relevant data changes.
  • Anyone can search across tasks, projects, and comments they have access to, ranked by relevance.
  • A project's tasks can be exported to CSV on demand; the requester is notified when the file is ready.
