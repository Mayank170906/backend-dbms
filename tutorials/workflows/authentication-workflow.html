Authentication Workflow

The JWT lifecycle, told as a user journey rather than a wire-protocol diagram.

For the step-through technical diagram of this same flow, see Architecture → Authentication Flow. This page tells the same story from the user's side.

  1. A new user registers once. From then on they log in with username + password.
  2. A successful login hands the frontend an access token (used on every request for the next 30 minutes) and a refresh token (valid 7 days).
  3. When the access token expires, the frontend silently exchanges the refresh token for a new pair — the user never has to log in again mid-session. The old refresh token is immediately invalidated (rotation + blacklist), so a leaked, already-used refresh token can't be replayed.
  4. Logging out blacklists whatever refresh token the client currently holds, so it can't be used again even if it leaks afterward.
  5. Opening a real-time feature (the notification bell, a project's live activity tab) opens a WebSocket carrying the current access token as a URL parameter — the same 30-minute token, a separate authentication path from the HTTP one.
