Codebase: Project Structure

The repository tree, annotated by what each entry actually does.

backend-dbms/
├── apps/                    9 Django apps — see Applications
├── config/                  project package: settings, urls, asgi/wsgi, celery
│   └── settings/
│       ├── base.py          shared settings
│       ├── development.py   DEBUG=True, permissive CORS, insecure-key fallback
│       └── production.py    DEBUG=False, hard env-var guards, HTTPS/HSTS
├── tests/                   17 pytest files — all tests live here, not per-app
├── docker/
│   └── entrypoint.sh        waits for Postgres before exec'ing the container command
├── templates/                server-rendered pages (dashboard/login/etc.), zero ORM access
├── static/                   STATICFILES_DIRS source (pre-collectstatic)
├── staticfiles/               STATIC_ROOT — collectstatic output, WhiteNoise-served
├── media/                     MEDIA_ROOT — user uploads (avatars, exports); local filesystem, not object storage
├── tutorials/                 this documentation site
├── Dockerfile
├── docker-compose.yml         dev stack: db, redis, web, worker, beat
├── docker-compose.prod.yml    prod stack: no bind mount, daphne, .env.production
├── pyproject.toml / uv.lock   dependency management (no requirements.txt)
├── manage.py                  defaults DJANGO_SETTINGS_MODULE to development
├── .env.example / .env.production.example
└── .github/workflows/deploy-tutorials.yml   the only CI/CD in the repo (Pages deploy for this site)
Two entries at repo root are local runtime artifacts, not source: celerybeat-schedule (Celery beat's on-disk schedule database) and a stray empty static;C directory. Neither is meaningful to read or edit.

See Applications for what's inside apps/, and Configuration for what's inside config/settings/.
