Codebase: Permissions

The two real DRF permission classes — and why there aren't more.

Only two custom DRF permission classes exist in the whole codebase. Most access control is actually done by scoping querysets (see Multi-Tenancy Model), not by these two — they exist specifically for object-level write checks a queryset filter can't express.

IsOrganizationAdmin

apps/organizations/api/permissions.py — object-level only.

  • Safe methods (GET/HEAD/OPTIONS): require an existing Membership.
  • Unsafe methods (POST/PUT/PATCH/DELETE): require Membership.role in [OWNER, ADMIN].

IsProjectManager

apps/projects/api/permissions.py — object-level only.

  • Safe methods: require an existing ProjectMembership.
  • Unsafe methods: require role == MANAGER.

Why not more permission classes

Most authorization questions in this project are actually "does this row belong to a tenant/project I'm a member of" — which is answered by filtering get_queryset(), not by a permission class evaluated per-object after the fact. That's also what produces the 404-vs-403 behavior: a non-member's request never reaches a permission check for an object it can't see, because the object was never in its queryset to begin with. See API → Error Handling.
